## 2. КЛАССИФИКАЦИЯ ЗАДАЧ (ТРИАЖ / TRIAGE PROTOCOL)

Перед началом любой работы оцени масштаб задачи и выбери строго один из двух режимов:

### Режим А: Fast Track / Solo Mode (Одиночный режим)
- **Когда использовать:** обычное общение, ответы на вопросы, консультации, советы по архитектуре/библиотекам, правка конфигов, мелкие фиксы и точечные изменения (до 1–2 файлов).
- **Как выполняется:** главный оркестратор (`gemini-3.8-flash-high`) решает задачу **напрямую сам в один шаг**.
- **Запрет:** НЕ запускать саб-агентов (`scout`, `architect`, `coder`, `fixer`). Это экономит время, токены и сохраняет непрерывность живого диалога.

### Режим Б: Multi-Agent Pipeline (Командный консилиум)
- **Когда использовать:** разработка новых крупных фич, сквозной рефакторинг (>2–3 файлов), сложные изменения в слоях состояния/API или по прямому запросу пользователя.
- **Как выполняется:** строго по 5-шаговому жизненному циклу (см. Раздел 6).

## 6. АРХИТЕКТУРА ПРОЕКТА (DEV VS PROD)

1. **Фронтенд — чистый статический SPA:**
   - В production-режиме бандл `dist/` собирается через `npm run build` и обращается напрямую к внешнему API через переменную `VITE_FINANCE_API` из `.env` (см. `src/api/apiRouter.ts`).
   - В продакшене **нет Node.js бэкенда** и нет `server/prod.ts`. Для хостинга статики используется Nginx / CDN / S3.
2. **Мок-бэкенд — только для локальной разработки:**
   - Код в `server/` (`server/index.ts`, `server/endpoints/`) — это исключительно локальный стаб для dev-режима (`npm run dev:stub`, порт 3001).

## 7. АРХИТЕКТУРНЫЕ СТАНДАРТЫ СТРУКТУРЫ ПРОЕКТА (CONVENTIONS)

1. **Расположение типов (`src/types/`):**
   - Все доменные интерфейсы, DTO, модели сущностей хранятся СТРОГО в `src/types/<domain>.ts` (например, `cards.ts`, `currency.ts`, `helpCenter.ts`).
   - Запрещено создавать локальные `types.ts` внутри папок страниц (`src/pages/*/types.ts`). В компонентах допустимы только `interface Props`.
2. **Расположение компонентов (`src/components/`):**
   - ВСЕ переиспользуемые и составные UI-компоненты хранятся строго в `src/components/<ComponentName>/`.
   - Запрещено создавать вложенные папки `components/` внутри страниц (`src/pages/*/components/` — ЗАПРЕЩЕНО). В проекте нет FSD, используется чистая плоская модульная архитектура компонентов.
3. **Роль страниц (`src/pages/<PageName>/`):**
   - Страница — это чистый композиционный экран. Она содержит только `Page.tsx`, `Page.module.css`, специфичные хуки (например, `useCardManager.ts`) и интеграционные тесты страницы (`Page.test.tsx`).
4. **Атомарная декомпозиция (Atomic UI Decomposition):**
   - **Запрет инлайн-карточек:** любой элемент списка (`.map()`), имеющий структуру разметки, стили или кнопки, выносится в отдельный компонент рядом с контейнером списка (паттерн `CardList/CardItem.tsx`, `SupportCards/SupportCard.tsx`, `FaqAccordion/FaqItem.tsx`).
   - **Запрет инлайн-контролов в страницах:** поля поиска с кнопками очистки, фильтры и интерактивные панели выносятся в отдельные компоненты (`HelpSearchBar`, `HelpCategoryFilter`).

## 8. ЖИЗНЕННЫЙ ЦИКЛ ВЫПОЛНЕНИЯ ЗАДАЧИ (Pipeline Режима Б)

1. **Discovery:** Прочитай локальный `./GEMINI.md` проекта.
2. **Scout:** Прочитай профиль `scout.md` и запусти саб-агента для сбора контекста из кода, структуры `src/types/` и Obsidian.
3. **Plan:** Прочитай профиль `architect.md` и передай ему выжимку от `scout`. Архитектор ОБЯЗАН следовать стандартам Раздела 7 (типы в `src/types/`, компоненты в `src/components/`, глубокая атомарная декомпозиция).
4. **Execute:** Выполни код через `coder` (`gemini-3.8-flash-high`). При затыке >2 попыток — вызывай `fixer` (`claude-sonnet-4-4`).
5. **Verify:** Запусти тесты/линтеры/сборку и передай `git diff` агенту `architect` на проверку. Архитектор отклоняет (`STATUS: REJECTED`) код при нарушении правил декомпозиции или структуры папок.
